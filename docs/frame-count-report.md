# フレーム数が試合結果に与える影響 — 技術調査レポート

> **対象読者:** このプロジェクトに初めて参加する開発者・デザイナー。ゲームエンジンの内部構造を知らなくても読めるよう、基礎概念から順を追って説明する。

---

## 1. 問題の概要

ヘッドレスシミュレーション（バックグラウンドで自動実行する統計収集モード）と、ブラウザ上で実際にプレイした試合の間で、**ゴール数・シュート数に大きな乖離**が確認された。

| 指標 | ヘッドレス（VFAST設定） | 実際のゲーム（観測値） |
|------|----------------------|----------------------|
| ゴール数/試合 | 約 4 | **18** |
| シュート数/試合 | 約 16 | **52** |
| ゴール率（シュート→得点） | 31% | 35% |

ゴール率はほぼ同じであるにもかかわらず、ゴール数が **4.5倍** も異なっていた。本レポートでは、この乖離の根本原因を技術的に解説する。

---

## 2. 基礎知識：ゲームエンジンの動作原理

### 2-1. 「フレーム」とは何か

コンピュータゲームは、**1秒間に数十回から数百回、画面を更新する**ことで動きを表現している。この1回の更新を「フレーム」と呼ぶ。本プロジェクトのブラウザゲームは、標準的な **60fps（1秒間に60フレーム）** で動作する。

各フレームで行われることは以下の通りである。

1. 経過時間（`elapsed`）を計測する
2. `update()` 関数を呼び出し、選手・ボールの位置を計算する
3. `render()` 関数を呼び出し、画面を描画する

### 2-2. `dt`（デルタタイム）とは何か

`dt` とは「前のフレームからの経過時間（秒）」を指す。60fps で動作している場合、`dt ≈ 1/60 ≈ 0.0167秒` となる。`update()` 関数はこの `dt` を受け取り、「`dt` 秒分だけ物理演算を進める」という処理を行う。

### 2-3. `simDt`（シミュレーション時計の進み方）

本エンジンには、**現実の時間（physDt）** と **試合時計の進み方（simDt）** が分離して存在する。

```
simDt = physDt × speedMul
```

`speedMul` は速度モードに応じて変化する倍率である。`speedMul` が大きいほど、1フレームで試合時計が多く進む。

---

## 3. 速度モード（SpeedMode）の仕組み

本ゲームには6段階の速度モードが存在する。各モードの `speedMul` 値は `types.ts` で定義されている。

```typescript
// client/src/game/types.ts
export const SPEED_MULTIPLIERS: Record<SpeedMode, number> = {
  REAL:  240 / 5400,  // 0.0444 ← 現実のサッカーと同じ速度（90分かかる）
  VSLOW: 0.10,
  LOW:   0.15,
  MID:   0.40,        // ← デフォルト（「NORMAL」と表示）
  FAST:  1.0,
  VFAST: 2.0,         // ← 最速モード
};
```

### 3-1. 1試合に必要なフレーム数の計算

試合は「シミュレーション時計が `halfDuration × 2 = 240秒` 進んだら終了」という条件で制御されている（`constants.ts: halfDuration = 120`）。

1フレームで試合時計が進む量は `simDt/frame = rawDt × speedMul` であるから、1試合に必要なフレーム数は次の式で求められる。

```
必要フレーム数 = halfDuration × 2 ÷ simDt_per_frame
              = 240 ÷ (rawDt × speedMul)
              = 240 ÷ (1/60 × speedMul)
              = 14,400 ÷ speedMul
```

各モードの計算結果を以下に示す。

| モード | speedMul | simDt/frame（秒） | 必要フレーム数/試合 | 実測フレーム数 |
|--------|----------|-----------------|-------------------|--------------|
| REAL | 0.0444 | 0.000741 | 324,000 | — |
| VSLOW | 0.10 | 0.001667 | 144,000 | — |
| LOW | 0.15 | 0.002500 | 96,000 | — |
| **MID** | **0.40** | **0.006667** | **36,000** | **約 38,000** |
| FAST | 1.0 | 0.016667 | 14,400 | 約 15,500 |
| **VFAST** | **2.0** | **0.033333** | **7,200** | **約 7,700** |

計算値と実測値がほぼ一致していることが確認できる（誤差はゴール後の待機時間などによる）。

---

## 4. フレーム数がゴール数に比例する理由

### 4-1. 1フレームで行われる処理

`update()` が1回呼ばれるたびに、以下の処理が実行される。

- 各選手のAIが「パス・シュート・ドリブル」を判断する
- ボールが移動し、ゴールライン・サイドラインとの衝突判定が行われる
- シュートが打たれた場合、GKがセーブ判定を行う

この処理は `update()` が呼ばれるたびに **毎回** 実行される。つまり、`update()` の呼び出し回数が多いほど、選手がシュートを打つ機会が増え、結果としてゴール数も増加する。

### 4-2. 比例関係の確認

```
ゴール数 ∝ シュート数 ∝ update()の呼び出し回数 ∝ フレーム数
```

実測データでこの比例関係を確認する。

| モード | フレーム数/試合 | ゴール数/試合（実測） | 比率 |
|--------|--------------|---------------------|------|
| MID | 36,000 | 20.4 | 5.1× |
| FAST | 14,400 | 8.6 | 2.2× |
| **VFAST** | **7,200** | **4.0** | **1.0×（基準）** |

MID ÷ VFAST のフレーム数比は **5.0倍**、ゴール数比は **5.1倍** であり、ほぼ完全に比例している。

### 4-3. 物理演算（選手の動き）への影響はないのか

重要な点として、**物理演算の精度はspeedModeに依存しない**。`engine.ts` のバージョン v11.36.0 以降、物理dtはspeedMulから独立して計算される。

```typescript
// engine.ts（抜粋）
const PHYS_SCALE = 10.8;             // MIDベースライン（27.0 × 0.40）
dt = physDt * PHYS_SCALE;            // 物理dt: speedMulを使わない
const simDt = physDt * speedMul;     // 試合時計: speedMulのみ
```

各モードの物理dt（`update()` 1回あたり）を計算すると、いずれも同じ値になる。

| モード | physDt/call（秒） | 物理dt（秒） |
|--------|-----------------|------------|
| MID | 0.00833 | 0.0900 |
| FAST | 0.00417 | 0.0450 |
| VFAST | 0.00208 | 0.0225 |

> **注意:** subSteps（1フレームあたりの `update()` 呼び出し回数）が異なるため、physDt/call は異なるが、物理dtは全モードで同一である。

つまり、選手の走る速度・ボールの飛び方・GKのセーブ判定の精度は、どの速度モードでも**まったく同じ**である。速度モードが変わるのは「1試合に何回 `update()` が呼ばれるか」だけである。

---

## 5. subSteps（サブステップ）の役割

VFASTモードでは1フレームあたり8回 `update()` が呼ばれる。これは「サブステップ分割」と呼ばれる技術で、ボールが高速移動する際にゴールラインをすり抜けないようにするためのものである。

```typescript
// Home.tsx（抜粋）
const subSteps = speed === 'VFAST' ? 8 : speed === 'FAST' ? 4 : speed === 'MID' ? 2 : 1;
const dt = rawDt / subSteps;  // 1回あたりのdtを小さくする

for (let _s = 0; _s < subSteps; _s++) {
  update(stRef.current, dt);  // subSteps回呼ぶ
}
```

重要なのは、subStepsを増やしても **simDt/frame（1フレームあたりの試合時計の進み）は変わらない** という点である。

```
simDt/frame = (rawDt / subSteps) × speedMul × subSteps = rawDt × speedMul
```

subStepsは分子と分母に同時に現れるため相殺される。

---

## 6. ヘッドレスシミュレーションとの比較

### 6-1. ヘッドレスの設定

`headless-sim.ts` では、以下のように `update()` を呼び出している。

```typescript
const SIM_DT = 1 / 60;  // 60fps相当
st.speed = "VFAST";     // speedMul = 2.0

while (!st.over && frames < maxFrames) {
  update(st, SIM_DT);   // サブステップなし、1フレーム1回
  frames++;
}
```

この場合の simDt/frame を計算する。

```
simDt/frame = SIM_DT × speedMul = (1/60) × 2.0 = 0.03333秒
必要フレーム数 = 240 ÷ 0.03333 = 7,200フレーム
```

### 6-2. ブラウザゲーム（VFAST）との比較

| 項目 | ヘッドレス（VFAST） | ブラウザ VFAST |
|------|-------------------|--------------|
| rawDt | 1/60 | 1/60 |
| speedMul | 2.0 | 2.0 |
| subSteps | 1 | 8 |
| dt/call | 1/60 | 1/480 |
| simDt/frame | **0.03333秒** | **0.03333秒** |
| フレーム数/試合 | **7,200** | **7,200** |
| 実測ゴール数 | **4.0** | **3** |

simDt/frame が同じであるため、フレーム数も同じ、ゴール数も同じになる。**ヘッドレスとブラウザVFASTは完全に等価**である。

---

## 7. 今回の乖離の根本原因

前回の観測試合（BLU 9-9 RED、18ゴール）は、**VFASTモードではなくMIDモードで実行されていた**。

### 7-1. なぜMIDで動いていたのか

ゲーム開始時のデフォルト速度は `MID` である（`useState<SpeedMode>("MID")`）。前回の試合では、V.FASTボタンをクリックしたが、クリックが正常に反映されなかった（またはゴールリプレイ表示中にクリックが無効化された）と推定される。

### 7-2. MIDとVFASTの数値比較

| 項目 | MID（前回の試合） | VFAST（今回の検証） |
|------|-----------------|-------------------|
| フレーム数/試合 | 36,000 | 7,200 |
| フレーム数比 | **5.0倍** | 1.0倍（基準） |
| ゴール数/試合（実測） | **18** | **3〜4** |
| ゴール数比 | **4.5〜5.1倍** | 1.0倍（基準） |

フレーム数比とゴール数比がほぼ一致しており、**フレーム数の差がゴール数の差を説明している**ことが確認できる。

---

## 8. 結論と推奨事項

### 8-1. 結論

本調査の結論を以下にまとめる。

1. **フレーム数とゴール数は比例する。** 1フレームで `update()` が1回呼ばれ、そのたびに選手がシュートを打つ機会が生じるため、フレーム数が多いほどゴール数も多くなる。

2. **フレーム数は speedMul に反比例する。** `speedMul` が大きいほど1フレームで試合時計が多く進むため、試合終了までに必要なフレーム数が少なくなる。

3. **物理演算の精度はspeedModeに依存しない。** 選手の動き・ボールの挙動・GKのセーブ判定は全モードで同一であり、速度モードはあくまで「試合時計の進み方」のみを制御する。

4. **ヘッドレスとブラウザVFASTは等価である。** 同じ `speedMul` を使用している限り、simDt/frame が同じになるため、統計的に同等の結果が得られる。

5. **今回の乖離はMIDモードで試合が実行されたことが原因である。** VFASTで正しく実行した場合、ヘッドレスと実際のゲームの結果は一致する。

### 8-2. 推奨事項

| 課題 | 推奨対応 |
|------|---------|
| ゲーム開始時のデフォルト速度がMID | キックオフ前の選択画面で速度を設定できるようにする、またはデフォルトをVFASTに変更する |
| ヘッドレスの速度設定がVFASTに固定 | 統計収集目的であれば問題ないが、MIDで実行する場合は5倍の時間がかかることを留意する |
| 速度モード変更がリプレイ中に無効化される可能性 | リプレイ中の速度ボタンのクリックが確実に反映されるよう実装を確認する |
