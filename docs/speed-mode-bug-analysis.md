# 速度モードバグ 根本原因分析

## 問題1: モードによってシミュレーション結果が異なる

### 根本原因

v11.36.0で「物理dtをspeedMul非依存にする」修正が入ったが、**不完全**。

`update()` 内で `dt = physDt * PHYS_SCALE` に再代入されるが、
呼び出し元（Home.tsx）が `subSteps` で分割して呼ぶため：

```
Home.tsx:
  subSteps = VFAST:8, FAST:4, MID:2, SLOW:1
  dt_per_call = rawDt / subSteps
  → update()を subSteps 回呼ぶ

engine.ts update():
  physDt = dt_per_call  (= rawDt / subSteps)
  dt = physDt * 10.8    (物理dt)
  simDt = physDt * speedMul  (試合時計dt)
```

**問題**: 1フレームあたりの総物理dt:
- MID:  2 × (rawDt/2) × 10.8 = rawDt × 10.8 ✓
- FAST: 4 × (rawDt/4) × 10.8 = rawDt × 10.8 ✓  
- VFAST: 8 × (rawDt/8) × 10.8 = rawDt × 10.8 ✓

→ 1フレームあたりの物理dtは同じ！

**しかし**: 1フレームあたりの試合時計dt:
- MID:  2 × (rawDt/2) × 0.40 = rawDt × 0.40
- FAST: 4 × (rawDt/4) × 1.0  = rawDt × 1.0
- VFAST: 8 × (rawDt/8) × 2.0  = rawDt × 2.0

→ VFASTはMIDの5倍速く試合時計が進む → 試合が5倍早く終わる → フレーム数が1/5

**つまり**: 物理dtは同じだが、VFASTは試合が早く終わるので
「物理演算の回数」が少ない → シュート機会が少ない → ゴールが少ない

### これは仕様か？バグか？

これは**設計上の問題**。速度モードの目的は「試合を早く見る」こと。
VFASTで試合が2分で終わるなら、MIDの7.5分と比べて物理演算回数が少ないのは当然。

**しかし**、ゲームバランスの観点では問題：
- VFASTで4ゴール/試合、MIDで20ゴール/試合は大きすぎる差
- ヘッドレスシミュレーションの結果がゲーム画面と一致しない

### 修正方針

**アプローチA: 試合時計を物理フレーム数に基づいて進める**
- 全モードで同じフレーム数を実行し、試合時計は固定フレーム数で進める
- speedMulは「1フレームあたりのupdate()呼び出し回数」にのみ影響
- メリット: 完全に同一の試合結果
- デメリット: VFASTでも同じ実時間がかかる（意味がない）

**アプローチB: speedMulを「フレームスキップ」として実装**
- 全モードで同じ物理dt × 同じフレーム数を実行
- speedMulは「何フレームに1回描画するか」にのみ影響
- VFASTは8フレームに1回だけ描画、残り7フレームは描画スキップ
- メリット: 完全に同一の試合結果、かつ高速
- デメリット: 描画がカクカクする（許容範囲）

**アプローチC（推奨）: 1フレームあたりのupdate回数をspeedMulで増やす**
- 全モードで「1実時間秒あたりの物理演算回数」を同じにする
- VFASTでは1フレームあたり多くのupdateを呼ぶ（現在のsubStepsを拡張）
- simDtはupdate内で固定値にする（speedMul非依存）
- メリット: 同一の試合結果、かつ高速描画
- デメリット: CPU負荷が高い（VFASTで多くのupdate呼び出し）

## 問題2: 速度モードが切り替わらない

### 根本原因

Home.tsxでspeedボタンのonClickが `stRef.current.speed` を更新するが、
ゴールリプレイ中はゲームループの先頭でリプレイモードに入り、
`stRef.current.speed` の読み取りがスキップされる。

ただし、実際にはstRef.current.speedは正しく更新されている（コンソールで確認済み）。
前回の試合で切り替わらなかったのは、ボタンクリックがリプレイUIに吸収された可能性。

### 修正方針
- リプレイ中もspeedボタンを有効にする
- speed変更時にvisual feedbackを強化する
